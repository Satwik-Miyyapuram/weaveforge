# WeaveForge — Android TWA (Trusted Web Activity)

Wraps the deployed PWA (`https://app.weaveforge.org`) into an
installable Android APK/AAB. Same web code — the APK is a thin Chrome wrapper.
Once the domain is verified via Digital Asset Links, the URL bar is hidden.

## Releases

Android ships on **`android-v*`** tags (e.g. `android-v6`). Python SDK uses
**`vX.Y.Z`**. See [docs/building/release.md](../../../docs/building/release.md).

```bash
# after bumping appVersion* in twa-manifest.json and merging to main:
git tag android-v6   # the number is appVersionCode, not the app version
git push origin android-v6
```

## What is committed, and what is not

The Android project is **source**, and it is committed: `twa-manifest.json`,
`app/build.gradle`, `build.gradle`, `settings.gradle`, `gradle.properties`, the
Gradle wrapper (`gradlew`, `gradlew.bat`, and the jar and properties under
`gradle/wrapper/`), and everything under `app/src/` — the manifest, the three
Java classes and every resource. Hand edits made there are reviewed like any
other change, and a clone can build the same APK. The ignore rules in
`.gitignore` cover only what the build *produces*: `app/build/`, `build/`,
`.gradle/`, `*.apk`, `*.aab`, `*.jks`, `manifest-checksum.txt` and
`store_icon.png`.

`gradlew` is committed **executable** (`git add --chmod=+x apps/web/twa/gradlew`).
Bubblewrap runs it as `./gradlew` on anything that is not Windows, and a Windows
checkout records `100644` for a new file by default — a clone that records
nothing would fail on the runner with a bare "Permission denied". The release
workflow asserts the bit rather than fixing it up, so the repository stays
buildable for everyone.

This matters because Bubblewrap does not treat the project as source. Both
`bubblewrap init` and `bubblewrap update` call `TwaGenerator.removeTwaProject()`
and then write the entire Gradle project out again from the CLI's bundled
template — so an `update` in CI would silently replace the committed tree with
whatever that version of the CLI generates, and any hand edit would be gone
without appearing in a diff. The release workflow therefore runs
`bubblewrap build` against the committed project and **not** `update`.

The one thing `update` contributes — a project that matches
`twa-manifest.json` — is checked directly instead. The workflow compares the
manifest against `app/build.gradle` and `app/src/main/AndroidManifest.xml`
field by field and fails on any mismatch. Locally, `bubblewrap update` followed
by `git diff` should show no change to the Gradle files; the regenerated
`mipmap-*` icons are the exception, because they are re-downloaded from the
deployed site each time (see below). If the Gradle files do differ, either the
manifest or the committed project is wrong; decide which, and commit the result.

## Prerequisites (local machine, one time)

- JDK 17+ (`java -version`)
- Android SDK / command-line tools (Bubblewrap can fetch these on first run)
- Bubblewrap CLI, **pinned**:
  `npm i -g @bubblewrap/cli@1.24.1`
- Repo secrets: `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_PASSWORD`, `ANDROID_KEY_ALIAS` (see `.github/workflows/android-twa.yml`)

### Why the CLI version is pinned

The committed project was generated by the 1.24.x template line, and the
template is where `compileSdkVersion`, `targetSdkVersion` and the Android
Gradle Plugin version come from — they are not read from `twa-manifest.json`.
The pinned version is coherent with what is committed: `compileSdkVersion 36`,
`targetSdkVersion 35`, `com.android.tools.build:gradle:8.9.1` and
Gradle 8.11.1, matching
`gradle/wrapper/gradle-wrapper.properties`. 1.25.0 moved its template to
`targetSdkVersion 36`, so `npm install -g @bubblewrap/cli` (which installs
whatever is current) would regenerate a materially different project and change
what a release tag means. Bump the pin and regenerate the project in the same
commit, or not at all.

## Local build

```bash
# From apps/web/twa
bubblewrap build
# → app-release-signed.apk + app-release-bundle.aab
```

`bubblewrap build` asks "would you like to regenerate your project?" when
`manifest-checksum.txt` is missing or does not match `twa-manifest.json`, and
CI has no stdin to answer it. The release workflow writes the checksum itself —
it is the SHA-1 of the manifest bytes, which is exactly what Bubblewrap's
`computeChecksum` produces:

```bash
node -e "process.stdout.write(require('crypto').createHash('sha1').update(require('fs').readFileSync('twa-manifest.json')).digest('hex'))" > manifest-checksum.txt
```

To regenerate the project from the manifest (only when you intend to change the
committed Gradle project):

```bash
bubblewrap update --skipVersionUpgrade   # removes and rewrites app/ from the template
git diff                                 # review everything it replaced
```

`bubblewrap init` creates a project from scratch and needs the web manifest at
`apps/web/public/manifest.webmanifest`; it also creates the keystore. Do not
run it over a checkout whose `app/` you mean to keep.

## Digital Asset Links (fixes the Chrome URL bar)

Chrome verifies the app against the certificate it was **signed with on the
device**, which is not always the certificate we sign with. An APK people
sideload is signed with the upload key from `android-keystore.jks`; the same
build uploaded to Play is **re-signed by Play App Signing**, and an install
from Play therefore carries Play's app-signing certificate instead. Both
fingerprints have to be listed, or exactly one class of install shows the URL
bar and looks broken.

`apps/web/public/.well-known/assetlinks.json` contains one entry per
certificate. The first is the upload keystore's real SHA-256. The second is a
deliberate placeholder — `REPLACE_WITH_PLAY_APP_SIGNING_CERT_SHA256` — because
the app-signing certificate only exists once Play App Signing has been enabled
for the app, and it cannot be derived from this repository. It is not a valid
fingerprint and cannot be mistaken for one; nothing verifies against it. The
release workflow warns while it is still in place.

1. **Upload certificate** — the keystore we hold:
   ```bash
   gh workflow run android-fingerprint.yml      # prints it in the job summary
   # or, locally:
   keytool -list -v -keystore android-keystore.jks -alias weaveforge
   ```
   Copy the `SHA256:` line into the first entry's `sha256_cert_fingerprints`
   in `apps/web/public/.well-known/assetlinks.json`.
2. **Play app-signing certificate** — Play holds this, not us. In the Play
   Console, open the app, then *Release → Setup → App integrity → App signing
   key certificate* and copy **SHA-256 certificate fingerprint**. Paste it over
   the placeholder in the second entry. (This is only meaningful once the app
   is enrolled in Play App Signing; if Play is signing with the upload key
   instead, the two fingerprints are identical and the second entry can be
   deleted.) Play Console's own copy is the only authoritative source — a
   `keytool -printcert -jarfile app-release-bundle.aab` reads the *upload*
   signature, because that is the signature we put on the file, not the one
   Play will replace it with.
3. Deploy the web app so
   `https://app.weaveforge.org/.well-known/assetlinks.json`
   serves both values.
4. The release workflow asserts, before every build, that the file contains a
   statement for this package whose relation is
   `delegate_permission/common.handle_all_urls` and whose fingerprints include
   the keystore's SHA-256. The package name it checks against is read from
   `app/build.gradle`, so a rename that misses the JSON fails the build instead
   of shipping an unverified app.

Reinstall the app after assetlinks propagates (sometimes needs a few minutes +
clearing Chrome's Digital Asset Links cache / reinstall).

## Icons come from the deployed site, and are then committed

`twa-manifest.json` points `iconUrl`, `maskableIconUrl` and `webManifestUrl` at
the **deployed** site (`https://app.weaveforge.org/icons/icon-512.png` and
friends). Bubblewrap fetches those while it *generates* the project and writes
the per-density results into `app/src/main/res/mipmap-*` — so the committed
icons were authored by that download, and nothing in this repository decided
what they look like. The same generation pass writes the splash image.

Two consequences follow, and neither one is fixed by pinning the CLI:

- The APK carries the icons as they were when the project was last generated,
  not as the site serves them today. An icon change on the deployed site does
  **not** change the APK until someone runs `bubblewrap update` and commits the
  new `mipmap-*` files, where the change is reviewable.
- Regenerating is not byte-reproducible, because it reads a network resource
  that the repository does not pin by hash. Two builds of the same tag can
  therefore differ for reasons no diff here shows.

The release workflow narrows that gap instead of hiding it. Before each build it

- downloads the icon, the maskable icon and the web manifest from the deployed
  site,
- asserts the icons are square PNGs of at least 512×512 (Bubblewrap will not
  generate a mipmap set from anything smaller) and that the web manifest parses
  and still advertises both icon files,
- writes each asset's SHA-256 to the job summary.

A tag rebuild that produces a different APK can then be explained: compare the
recorded hashes between the two runs, then the artifact's own hash.

## Notes

- `android-keystore.jks` is gitignored — losing it means you cannot update the
  same app identity.
- Package id: `app.weaveforge.twa`. Changing it = a different app, and it
  appears in three places that the release workflow keeps in agreement:
  `twa-manifest.json`, `app/build.gradle` and
  `app/src/main/AndroidManifest.xml`.
- Bump `appVersion` / `appVersionName` / `appVersionCode` in `twa-manifest.json`
  for each Android release, and update `versionCode` / `versionName` in
  `app/build.gradle` to match — the workflow fails if they disagree.
