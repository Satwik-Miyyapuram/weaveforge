05

Three named measures instead of one 760px

ui-spec.md:115 states "desktop max-width matches the rest of the app (~760px)" as a consistency rule. 760px is a reading measure — about 75 characters at 15px. It is right for a log body and wrong for a five-column compare table and a force graph.

Now — everything at 760px shipped
runs table — 5 metric columns + name + checkbox, scrolling sideways inside 760px
The dashboard is worse: a 12-column grid inside 760px is 63px per column, so a 4-col card is 253px and its stat ring has no room for a label.
Change — each screen declares its measure proposed
--measure-prose760px — log, summaries, report, notes
--measure-data1120px — compare table, experiments, git
--measure-widemin(100vw − 2rem, 1600px) — graph, dashboard
The dashboard keeps 12 columns only above 1200px and drops to 6 at prose width. Three tokens, and every screen says which one it is.

Heading help: an inline disclosure, not a hover tooltip

a11y

There is no tooltip in the app today — no HeadingHelp component exists — so "every heading has a ? hover tooltip" is prospective, not shipped. It is worth deciding now rather than building it: a hover tooltip on a PWA that renders as a bottom-tab mobile app is unreachable on touch, and WCAG 1.4.13 requires a tooltip to be dismissible, hoverable and persistent. An inline disclosure satisfies all three with no JS.

Proposed-then-not-built — hover ? absent
Papers ?
On a phone: no hover state exists, so the help is unreachable. On a keyboard: focus alone does not reveal it.
Change — a disclosure under the heading proposed
Papers
Everything you have added, with the status you set. The graph and the report are built from this list — a paper is never "in" only one place.
One registry keyed by ScreenId, so the copy lives in one file and every screen has it. Renders identically at every breakpoint; takes the prose measure.
11

The metric curve: give it an actual design

decision 3

Curves are drawn with uPlot, and the spec concedes the styling "needs design". This is the product's evidence: a loss curve exists to show a spike. The code audit's chunking work already chose a stride over an average for exactly this reason — so a smoothing control in the UI would undo at the chart what the query layer was careful to preserve.

Change — no smoothing, one shared y-domain recommended
run 14 · loss run 9 · loss (dashed = validation)
1.5px strokes, round joins, crosshair listing every visible series at the nearest step. Free scale is an explicit opt-out, never the default — independent y-scales make a worse run look like a better one, which is the failure the module exists to prevent.
The alternative — a smoothing slider not recommended
smooth
At step 60k–70k the divergence — the entire reason to plot two runs — is gone. If smoothing ever ships it must be a named preset and the axis must say so.

Dashboard rings: one gauge, not six

Six default student cards each carry a progress ring, and §3.0 concedes "card chrome, stat rings and edit affordances need a final pass". Appendix A specifies radius and shadow and stops before any data primitive, so six gauges cannot agree on stroke width, tick position, label placement, or what the remainder arc means.

Now — nothing to conform to shipped
Two different radii, two stroke widths, two colours for the same idea — and the remainder arc means something different in each.
Change — one Ring, thresholds from the ramp proposed
progress · 72%
r=22 · 4px round cap · tabular numeral · label below at 12px mono
Value arc takes --s-good / --s-warn / --s-danger by threshold — the same ranks as the status pills, so a ring and a pill agree that 80% is good. Defined in Appendix A beside the radius and shadow tokens.

The decisions, and my recommendation

# The choice My call
1 Group the 14 settings tabs · or leave the strip Group. Six groups on a rail, above.
2 One card density · or two, with a text-first Entry Two. The hidden-summary argument is the strongest finding in the review.
3 No smoothing, shared scale · or a smoothing slider No slider. The query layer already refuses to average.
4 Keep 4 destinations + breadcrumbs · or five task groups (Capture · Read · Run · Write · Share) Breadcrumbs now, destination set later. All three proposals disagree, and the accessible half is not preference — it needs a card sort, not a mock.
5 A Lab card on Home first · or the Org tab only Home card first. Lab formation is the acquisition loop and has no entry point.
