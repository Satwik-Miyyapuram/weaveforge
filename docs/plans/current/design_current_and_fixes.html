1 · Settings

biggest correction

Both models, and ui-spec §3.13, describe "one seven-section scroll, candidate for tabs". The screen is already a 14-tab tablist with real role="tablist" / role="tab" / role="tabpanel" and aria-labelledby wiring (settings-screen.tsx:49-64, :318-339). The problem is not the absence of tabs — it is that there are fourteen of them behind a horizontally-scrolling segmented control.

2 · The entity card

mostly already fixed

The audit says delete is "14px red text sitting next to edit". It is not. EntityCard renders an entity-icon-btn danger card-del — an icon button with aria-label, title and a danger class — pinned to the left of the foot, with status and actions grouped on the right. Four foot variants across screens were the real drift, and one primitive now serves all of them.

3 · Status vocabulary

ramp exists, one thing missing

The fault line both models describe — "each feature invented pill colours" — is closed. The --st-* family is defined once in themes/common.css and aliased onto the --s-* source ramp, which every theme sets. What is missing is the *component* and the gate, not the ramp.

4 · The shell — desktop rail and mobile bar both exist

differs from the audit

nav.css is mobile-first: an icon+label bar pinned to the bottom, becoming a left sidebar at the desktop breakpoint. So Model 2's "put a left rail in Settings" is new, but "add a left rail" is not a new idea here — the shell already has one. What is actually undecided is the destination set, and the two models give three different answers.
